# Feature Memory Methodology Gap

## 目的

本文档用于对比：

- 当前 [train/METHODOLOGY.md](/Users/ts-changchang.zhuang/git/money/train/METHODOLOGY.md) 已表达的方法论
- 2026-03 新提出的“特征记忆驱动”目标态
- 当前代码实现仍然存在的差距

核心结论是：

当前系统已经从“未来信息泄漏的旧训练方式”切换到了 `history-only rolling`，
但它还没有真正变成“随着时间推进持续积累特征记忆，并优先复用历史经验”的系统。

## 新观点的核心定义

目标态不是：

- 每个月都对同一批固定参数网格做全量回测排序；
- 再从其中挑出当月最优策略；
- 用这些结果去解释该月结构。

目标态应该是：

1. 对每个时间窗口提取市场特征向量。
2. 为每个特征向量保存当时验证后的最佳策略组合、风险动作、样本数和置信度。
3. 随着时间推进，特征库和策略库不断扩充。
4. 未来遇到相似特征时优先直接复用策略池。
5. 如果没有匹配特征，则进入保守模式或小规模探索模式。
6. 等该窗口结束后，再把“新特征 + 最佳策略组合”回写进知识库。

一句话说：

**系统的学习对象应当是“特征记忆库”，而不是“固定参数网格的重复月度排名”。**

## 与现有 METHODOLOGY 的一致部分

当前 `train/METHODOLOGY.md` 已经成立、并且与新观点一致的部分有：

- 单品种单独训练。
- 候选池优先于 Top1。
- 未来验证优先于训练内表现。
- 月/周/日/亏损反馈的分层决策结构。
- 强调市场特征驱动，而不是单个万能参数。

这些部分不需要推翻。

## 与现有 METHODOLOGY 的关键差异

### 1. 候选池的含义不同

当前文档更偏向：

- 先定义一个策略家族
- 生成参数网格
- 得到候选池
- 再按场景映射

新观点进一步强调：

- 候选池不应长期等于一个固定网格
- 它应该随着 rolling 学习不断扩充、淘汰和修正
- 参数集本身也应成为学习对象，而不是固定输入

### 2. rolling 的目标不同

当前文档中 rolling 更偏向：

- 用未来区间验证 router 和候选池是否有效

新观点要求 rolling 还必须回答：

- 系统是否越来越能直接命中已有特征记忆
- 未命中特征时是否能安全保守
- 新特征回写后后续是否更稳定

也就是说，rolling 不只是验证收益，还要验证“记忆库是否在成长”。

### 3. 特征的地位不同

当前文档里：

- 特征更像 router 的输入材料
- bucket 更像解释和规则生成的标签

新观点里：

- 特征记忆本身才是最核心资产
- router 只是把特征记忆转成可执行规则的表达层

应该沉淀的是：

- `feature vector`
- `matched candidate pool`
- `best strategy / best params`
- `risk action`
- `confidence`
- `sample count`

### 4. 未知场景的处理不同

当前方法更偏：

- 先训练候选池
- 再在验证中比较哪些策略更好

新观点要求：

- 如果未来窗口无法匹配到足够相似的历史特征
- 系统应默认进入保守模式
- 而不是继续从固定大网格中“重新挑一个冠军”

这会让系统更像一个会承认“不认识当前市场”的机器。

### 5. 回测的用途不同

当前实现里，大回测仍然承担：

- 每个月对固定候选集合重新排序

新观点要求大回测逐步转为：

- 冷启动时发现新策略
- 遇到未知特征时补充知识库
- 而不是每个月都重复跑完整大网格

## 当前代码实现与目标态的差距

截至当前版本，主要差距包括：

### 1. 仍存在固定大网格月月重排

虽然现在已是 `history-only rolling`，
但日志仍可能出现：

- `ranked 512/512 candidates`

这说明当前代码仍会在月度学习时对同一批固定参数组合做全量扫描。

这满足了“无未来泄漏”，但不满足“记忆式增长”。

### 2. 特征还没有作为独立知识库持久化

当前已有：

- rolling monthly pools
- rolling router rules
- rolling rule details

但还没有一套明确的：

- `feature_memory`
- `feature_strategy_matches`
- `unknown_feature_events`

因此系统还不能真正回答：

- 这个月为什么直接复用了某个历史特征
- 相似度是多少
- 为什么这次判定为未知场景

### 3. 候选池仍然更像“参数网格投影”

当前候选池的来源主要还是：

- `generateStrategyCombinations(...)`

目标态下，候选池应逐步转为：

- 固化过的策略组合库
- 过去窗口验证后沉淀下来的参数簇
- 与特征记忆联动维护的动态池

### 4. 未匹配特征的保守逻辑还不够明确

当前系统已有 `reduce/stop/loss_recheck`，
但这些更多是已知规则下的风险动作。

目标态还需要一条更底层的原则：

- 如果当前特征与历史库匹配度不足，先保守，不要强行交易。

## 建议的后续演进方向

下一阶段更推荐做的不是继续微调“512 参数空间”，而是：

### 1. 引入特征记忆主表

建议新增类似：

- `feature_memory`
- `feature_strategy_matches`
- `feature_candidate_pools`
- `unknown_feature_events`

### 2. 改写 rolling 主链路

把当前主链路从：

- `提取特征 -> 对固定网格全量回测 -> 排名 -> 生成 router`

逐步改成：

- `提取特征 -> 检索历史特征记忆 -> 复用候选池`
- `若未命中 -> 保守/探索`
- `窗口结束 -> 写回最佳策略与特征映射`

### 3. 把参数也视为学习对象

目标态不应只学习“哪种策略类型适合某种特征”，
还应学习：

- 哪组参数簇适合某类特征
- 哪些参数在某类特征下应该淘汰

### 4. 新增验证指标

后续报告建议新增：

- 特征命中率
- 未知特征占比
- 未知场景保守成功率
- 新特征回写后的二次命中率
- 策略池成长率

## 结论

`history-only rolling` 是必要的一步，但不是最终形态。

它解决的是：

- 不要用未来数据作弊

而新观点要解决的是：

- 不要每个月都重新做固定大网格的事后筛选
- 要让系统像一个会积累经验的策略机器

因此，真正的目标态应当定义为：

**特征记忆驱动的单品种自适应策略系统**
